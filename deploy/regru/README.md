# Перенос журнала на VPS REG.RU

Пакет рассчитан на PostgreSQL, GoTrue, PostgREST, Caddy и небольшой сервис управления учётными записями. База, авторизация, платный журнал и журнал КЦ работают на VPS. Текущие SQL-функции и RLS переносятся из действующей базы. Клиентский SDK хранится вместе с интерфейсом.

Для school используется API `https://api.muzjur.ru` на VPS и прежний адрес интерфейса `https://muzjur.ru` на GitHub Pages. Это позволяет переключить вход и сохранения без ожидания истечения DNS-кэша основного домена. VPS также может отдавать тот же интерфейс. Разрешённые источники CORS задаются через `ALLOWED_ORIGINS`; `SITE_URL` — основной адрес сайта, `DOMAIN` — адрес API. Секреты `.env` и резервные копии не публикуются.

Выбранная конфигурация — 2 vCPU, 2 ГБ RAM, SSD 20 ГБ, Москва. Расчёт REG.RU от 23 ноября 2026 года составляет 1169,41 ₽/месяц с публичным IP. Хранение копий REG.RU тарифицируется дополнительно. Рабочая ёмкость и время сохранений должны быть проверены после восстановления данных.

## До переключения

1. Создать VPS и получить SSH-доступ. Ограничить вход SSH ключом. Разрешить входящие 22, 80, 443. Порт базы наружу не публикуется.
2. Установить Docker Engine с Compose из официального репозитория. Установить ограничения журналов Docker и настроить обновления безопасности.
3. Скопировать проект на сервер, запустить `node deploy/regru/prepare.mjs test-journal.example.ru`. Скрипт создаёт приватный `.env` и каталог `public`, который содержит только клиентские файлы. Готовую папку можно собрать на машине с Node.js и затем передать на VPS.
4. Проверить `docker compose config --quiet`. Запустить из этой папки `docker compose up -d db accounts`. Настроить тестовый DNS и HTTPS. На первом запуске проверить совместимость версии GoTrue с таблицами Auth из источника.
5. В приватном `.source-db.env` задать переменные подключения источника `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`. Права файла 600. Из Database Settings источника скачать сертификат в `.source-ca.crt`. Выполнить `sh export-source.sh`, сохранить копию вне VPS. При необходимости использовать временный SSH-туннель, привязанный только к loopback: `SOURCE_TUNNEL_PORT=15433 sh export-source.sh`. Сертификат и имя исходного сервера продолжают проверяться. Файл подключения и SQL-дампы содержат секреты.
6. Выполнить `sh restore.sh import/TIMESTAMP` на пустой целевой базе. При ошибке восстановления остановиться и проверить совместимость схем. Скрипт завершает импорт до запуска публичного сайта.
7. Проверить вход существующими паролями, смену пароля, сброс администратором и роль преподавателя. Чужие журналы должны оставаться недоступными. Проверить обычный журнал, платные услуги, КЦ, группы, больничные, замещения и печать. Проверить параллельные сохранения и повтор после потери ответа.
8. Настроить ежедневный запуск `backup.sh`, контроль успешного завершения и отдельную копию вне сервера. Пробно восстановить копию в отдельную базу.

## Переключение

Выполнить `freeze-source.sql` в исходной базе в короткое окно обслуживания. Он дожидается завершения записей и блокирует новые изменения в школьных таблицах и Auth. Данные не удаляются. Приватная таблица `school_migration.write_guard` остаётся в источнике; её не включают в экспорт. `auth.schema_migrations` — управляемая служебная таблица, не меняется.

Сделать окончательный экспорт Auth и всех школьных схем и отдельную копию вне сервера. Для окончательного восстановления использовать новую пустую базу с инициализированной схемой Auth, указав её имя в `APP_DB`; проверенная пробная база сохраняется. После импорта выполнить `remove-target-guard.sql` только на VPS и сравнить все COPY-строки исходных дампов с повторным дампом восстановленной базы через `verify-copy.py`. До завершения сверки не разрешать новые записи. Обновить клиентскую конфигурацию основного сайта на API VPS и проверить вход, чтение и подтверждение сохранения. После смены сервера пользователям потребуется обновить страницу и заново войти. Вкладки с неподтверждёнными изменениями нельзя закрывать до переноса этих правок.

При откате до первых новых записей VPS можно снова разрешить запись в исходнике: `update school_migration.write_guard set frozen=false,changed_at=now() where singleton`. После начала записей на VPS сначала нужно сохранить и перенести эти записи обратно. Простой возврат старой конфигурации приведёт к расхождению данных.

`muzjur-backup.timer` запускает отдельный дамп активной базы каждую ночь в 03:00 по Екатеринбургу. Существующие копии автоматически не удаляются. Требуются независимая копия вне VPS и пробное восстановление; копия на том же диске не защищает от потери сервера.

Подготовка пакета не означает завершённый перенос. Покупка VPS, восстановление реальной базы, проверка на сервере и переключение DNS выполняются отдельно после получения доступа.
